# Phase 7 Plan 02: Remote images downloaded into the work directory

## Phase Goal

A template author can write ordinary image URLs in an HTML template, and one call to `HtmlImages` turns them into `cid:` references plus inline images that pass the Phase 5 checks.

This plan's slice: `http:` and `https:` image sources, opt-in through the work directory (HTML-05). Task 1 (tracer) downloads one image end to end into the work directory and sends it through `recording`. Task 2 pins every download rule against WireMock: status categories, redirect, content type, size cap, both timeouts, names, dedupe, concurrency, logging.

## Acceptance Criteria

- [ ] With a work directory, `embed` downloads `http(s)` images into it, with a 10 s connect timeout, one 30 s budget for the response and its body together (the body read gets only what the headers left of it), a 3 MiB cap (an image of 3 MiB or more is refused, as Graph refuses it) and an `image/` content type check; without one, it makes no request.
- [ ] Network errors, timeouts, 5xx and 429 are `TransientMailException`; every other non-success status, a non-image type and a body of 3 MiB or more are `InvalidMailException`; messages name the `src` and the status only; the DEBUG log record shows the URL without userinfo, query and fragment.
- [ ] All download tests run offline against WireMock; `./mvnw -B -ntp verify` and the scoped release build stay green; `morimail` is unchanged.

Planner choices (Claude's discretion; listed in the SUMMARY):
- P5: no Content-Length pre-check; `readNBytes((int) MAX_IMAGE_BYTES)` bounds the read for every response, with or without the header, and a result of `MAX_IMAGE_BYTES` bytes means the body is 3 MiB or more (A2).

- P8: a private record `Fetched(byte[] bytes, String contentType)` carries a download result; Plan 07-03 reuses it for `data:` sources.
- P9: the package-private overload `embed(MailTemplate, Path, Path, Duration requestTimeout)` is the test seam for the timeouts (GraphTransport precedent). Its Duration is the whole budget of one download (owner, 2026-11-23): the clock starts immediately before `HTTP.send`, `HttpRequest.timeout` gets the same Duration for the headers, and the body read waits only for what is left, so a download never gets a second full timeout. Bounding the redirect hops as well would need `sendAsync` with a cancelled future; this plan does not add it (Rule 0), and the Owner review asks the owner.
- Reader end (owner, 2026-11-23): the only mechanism is `close()` of the response `InputStream`. Research Stall3 and the planning experiment saw it end a blocked read at once with `IOException: closed`. No extra thread, executor, interrupt or wait.
