# Phase 1 Plan 06: Failure categories, scripted failures and configuration errors

## Phase Goal

**As a** Java developer, **I want to** build a templated mail and send it through a Mailer account, **so that** the core contracts are proven before any real transport.

This plan's slice: a test author scripts transient, permanent, sender-rejected and auth-required failures on the `recording` transport and sees each one surface from `Mailer` with its category; a misconfigured classpath or account fails at build time with a message that says what to fix; and one `Mailer` is safe to share between threads. It builds on the walking skeleton (plans 01-01, 01-03 and 01-04) and runs in parallel with plan 01-05, sharing no file.

## Acceptance Criteria

- [ ] `failNext`, `failFor` and `failValidation` script every failure category, and `Mailer` surfaces each with its type, without retrying.
- [ ] Duplicate ids, blank ids, broken providers, unknown transports, unknown accounts and bad `defaultFrom` values fail with the documented unchecked or checked exception.
- [ ] The concurrency test passes with 8 threads and 400 sends.

<objective>
Complete the RecordingTransport scripting surface (D-12, D-13), add the registry's duplicate-id and broken-provider rules (CORE-03), and pin the Mailer, MailAccount, error-tree and TokenProvider contracts with tests, including concurrent use.

Purpose: phase success criterion 4 and the frozen contracts Phase 2 (sample tests against recording) and Phase 3 (Graph and Entra) build on.
Output: the extended RecordingTransport and TransportRegistry, seven test classes, and defect fixes in Mailer or MailAccount only if a test exposes one.

Sizing note: the plan lists 11 files, above the 10-file warning threshold, while each task stays at five files or fewer. Seven of the 11 are test classes that pin contracts already built by plans 01-03 and 01-04; the planned production changes are the test fixture `RecordingTransport` and `TransportRegistry`, and `Mailer.java` and `MailAccount.java` are listed only for a defect fix if a test exposes one. Splitting off the test-heavy Task 3 would add a fifth wave (its concurrency test needs `attempts()` from Task 1) without reducing any single task. The estimate (70000 tokens) stays inside one executor's budget.
</objective>

## Assumptions (unresolved probe edges)

These probe rows were unclassified, so they stay unresolved and are carried as flagged assumptions rather than truths:

- **[edge CORE-02/unclassified]** The default freshAccessToken ignores rejectedToken and calls accessToken(scope) exactly once; a caching provider (Phase 3 EntraClientCredentials) overrides it to drop only a matching token.
- **[edge CORE-04/unclassified]** The core never inspects option values; a null option key or value makes MailAccount.Builder.build() throw NullPointerException from Map.copyOf (documented in 01-04), and each transport validates its own options (Phase 3 for graph).
- **[edge CORE-05/unclassified]** Mailer does not re-run the Mail.Builder checks on a Mail constructed directly from the records (RESEARCH Open Question 9); only the defaultFrom and no-sender rule and the transport's validate run. A Mailer with zero accounts is allowed and rejects every send as an unknown account.
- **[edge CORE-06/unclassified]** Mail.Builder and MailAccount.Builder are not thread-safe (documented); built Mail, MailAccount and Mailer objects are; RecordingTransport is thread-safe through one lock with no I/O inside it.
- **[edge CORE-07/unclassified]** failFor wins over failNext and does not consume the queue; failNext entries are consumed one per send in FIFO order; attempts() counts every send call; failed sends are not added to sent(); failValidation stays set until cleared with null.
- **[edge ERR-01/unclassified]** retryAfter is stored as a nullable Duration field and exposed as Optional<Duration>; no serialVersionUID is declared; the exceptions carry nothing transport-specific (the Graph error code and request-id arrive in the message text in Phase 3).
