# Phase 1 Plan 03: Walking skeleton, part 2 — the core contracts: build a plain mail, the error tree and the SPI

## Phase Goal

**As a** Java developer, **I want to** build a templated mail and send it through a Mailer account, **so that** the core contracts are proven before any real transport.

This plan is the second part of the Walking Skeleton (see `.planning/phases/01-library-core/SKELETON.md`): the developer builds a plain-text `Mail` and gets one clear `InvalidMailException` for an unsendable one, and a transport or token-provider author has the documented SPI and the full checked error tree to code against. Plan 01-04 wires these contracts through the registry, `MailAccount` and `Mailer` to the `recording` transport. It runs after the build skeleton (plan 01-01), in the same wave as plan 01-02, and shares no file with it.

## Acceptance Criteria

- [ ] `Mail.using("main").to(..).subject(..).text(..).build()` returns the mail; each unsendable variant fails with one `InvalidMailException` that names the field and never echoes the value.
- [ ] The six exceptions and the three SPI interfaces exist with the spec §5 signatures, and the release build is doclint-clean and produces the sources and Javadoc jars.

<objective>
Create the core model records, the plain `Mail.Builder`, the checked `MailException` tree and the three SPI interfaces (`MailTransport`, `TransportProvider`, `TokenProvider`), with doclint-clean Javadoc that states thread safety, plus `MailBuilderTest`.

Purpose: freeze the signatures every later plan and phase codes against (spec §5, CORE-02 owner decision) before any wiring depends on them.
Output: 13 core source files and `MailBuilderTest.java`.

Sizing note: the plan lists 14 files, above the 10-file warning threshold, and Task 1 (8 files) and Task 2 (6 files) are above the usual five-file task limit. The 13 sources are short declarations fixed by spec §5 (four records, six exception classes with two or three constructors each, three interfaces); the only logic is the `Mail.Builder` checks and the `MailAddress.invalidReason` helper, and `MailBuilderTest.java` is their one test. The signatures are frozen together because the release profile's doclint and the javap hierarchy check only prove them as a set, and splitting the exceptions or interfaces into their own plan would give a horizontal layer with no user-visible step and one more wave before plan 01-04. The estimate (50000 tokens) stays inside one executor's budget.
</objective>
