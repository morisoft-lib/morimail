# Phase 7 Plan 02: Remote images downloaded into the work directory

## Phase Goal

A template author can write ordinary image URLs in an HTML template, and one call to `HtmlImages` turns them into `cid:` references plus inline images that pass the Phase 5 checks.

This plan's slice: `http:` and `https:` image sources, opt-in through the work directory (HTML-05). Task 1 (tracer) downloads one image end to end into the work directory and sends it through `recording`. Task 2 pins every download rule against WireMock: status categories, redirect, content type, size cap, both timeouts, names, dedupe, concurrency, logging.

## Acceptance Criteria

- [ ] With a work directory, `embed` downloads `http(s)` images into it, with a 10 s connect timeout, a 30 s request timeout plus a 30 s read deadline, a 3 MiB cap and an `image/` content type check; without one, it makes no request.
- [ ] Network errors, timeouts, 5xx and 429 are `TransientMailException`; every other non-success status, a non-image type and a body over the cap are `InvalidMailException`; messages name the `src` and the status only.
- [ ] All download tests run offline against WireMock; `./mvnw -B -ntp verify` and the scoped release build stay green; `morimail` is unchanged.

Flagged assumptions (research recommendations; listed in the SUMMARY under "Owner review"):
- A2 (boundary part): "over the cap" means more than 3,145,728 bytes; exactly 3 MiB is accepted. The Graph transport later refuses a file of 3 MiB or more (Phase 5 D-15), so an image of exactly 3 MiB passes the helper and then fails Graph `validate`.
- A3: statuses that D-13 does not name map to `InvalidMailException` with the status only: an unfollowed 3xx (for example 304, or an https-to-http redirect), 1xx, 204 and 408. Any 2xx except 204 continues.
- A6 (Rule 0): no cleanup. Files that one call wrote before a later source failed stay in the work directory, which the caller owns and cleans up (D-04); the Javadoc says so.

Planner choices (Claude's discretion; listed in the SUMMARY):
- P5: no Content-Length pre-check; `readNBytes(MAX_IMAGE_BYTES + 1)` bounds the read for every response, with or without the header.
- P6: one `private static final HttpClient HTTP` field (D-14 allows it). The JDK starts its selector daemon thread when the class loads, also for local-only use; no holder class (Rule 0).
- P7: one DEBUG record per download naming the src; nothing else is logged.
- P8: a private record `Fetched(byte[] bytes, String contentType)` carries a download result; Plan 07-03 reuses it for `data:` sources.
- P9: the package-private overload `embed(MailTemplate, Path, Path, Duration requestTimeout)` is the test seam for the timeouts (GraphTransport precedent); the read deadline equals the request timeout.
- Remote reasons (fixed texts after `img src "SRC": `): `is not a valid URL`, `download failed`, `download failed with HTTP STATUS`, `download timed out`, `download was interrupted`, `response has no image content type`, `image is larger than 3 MiB`, `work directory is not usable`.
