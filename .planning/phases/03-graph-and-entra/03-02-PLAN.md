# Phase 3 Plan 02: Entra tokens with a certificate, cached safely, failing clearly

## Phase Goal

**As a** Java developer, **I want to** send mail through Microsoft Graph as an Entra app, **so that** each failure says whether to retry, drop the mail or fix the account.

This plan's slice: the Entra half. After it, a developer gets tokens with a certificate (key and certificate, or the PKCS12 file), the token is reused until five minutes before expiry with one request at a time, a rejected token is dropped only when it matches, and every token failure says transient or auth-required without ever carrying a secret. It builds on the secret-flow class from plan 03-01 and runs in the same wave as plan 03-03 (Graph), sharing no file with it.

## Acceptance Criteria

- [ ] The certificate flow works from the checked-in throwaway PKCS12, and the assertion matches the certificate-credentials page and verifies independently.
- [ ] The cache, the 5-minute margin, single flight and compare-and-drop are pinned by tests at their boundaries.
- [ ] Every token failure maps to TransientMailException or AuthRequiredException, timeouts included, and no secret, assertion, token or password appears in a log or a message.

## Flagged assumptions

- **Package-private test seam (RESEARCH Pattern 1, Assumption A4).** `forTest(Clock, Duration)` returns a copy with another clock and request timeout. It is package-private, used only by the same-package tests, and leaves the public API at the three factories plus `authority(URI)` (D-01, D-02). Without it the 5-minute boundary, the claim times and the timeout mapping could not be tested deterministically.
- **An unusable 200 is AuthRequiredException.** A 2xx body that is not JSON or lacks a non-empty access_token or a positive expires_in most likely means the authority points at something that is not Entra, which is an account setup problem: every mail of the account would fail. The live test can correct this.
- **3xx is AuthRequiredException.** Redirects are never followed (plan 03-01). A redirect from the token endpoint means a wrong authority, again an account setup problem.
- **Unclassified probe item ENTRA-06 (left unresolved).** Reviewed: compare-and-drop compares the whole token string with `equals`. Open: when the rejected token is no longer the cached one (another thread already refreshed), the newer cached token is returned without a request, and the Graph transport retries with it once; whether that newer token is accepted is the server's call.
- **Unclassified probe item ENTRA-09 (left unresolved).** Reviewed: the entra package writes no log records, and the log-capture test listens on the root java.util.logging logger, the backend of the default System.Logger. Open: a consumer with its own System.LoggerFinder is not covered by that test, but nothing is logged in any case.
- **Unclassified probe item TEST-01 (left unresolved).** Reviewed: the key store is generated with `keytool -J-Dkeystore.pkcs12.legacy`, which gives a SHA-1 MAC and 3DES/RC2 bags that every JDK reads (verified on JDK 21 here). Open: loading on JDK 17 is proven by the owner's Temurin 17 CI run after the push.
- **Unclassified probe item TEST-02 (left unresolved).** Reviewed: the signature is verified with a separate Signature instance and the certificate's public key, with a negative control. Open: whether the real Entra endpoint accepts PS256 is a STOP-report item of the owner's live test; there is no RS256 fallback.
