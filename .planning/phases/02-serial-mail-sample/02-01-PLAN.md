# Phase 2 Plan 01: Send a campaign once through recording, then dry-run it into rendered files

## Phase Goal

**As a** campaign sender, **I want to** dry-run and send a CSV serial mail with a journal, **so that** a rerun never mails a recipient twice.

This plan's slice: the `serial-mail send` command exists end to end. Through the CLI-12 seam it sends a CSV campaign once to the `recording` transport, journals every attempt, and a rerun sends nothing. The same command dry-runs a campaign into rendered files. The phase's planning files are scrubbed so that they can be published. Wave 2 then builds on this command: plan 02-02 makes pre-flight report every problem of a broken campaign, plan 02-03 adds retry, stop, pacing options and journal robustness, and plan 02-04 ships the example campaign and the runnable jar.

## Acceptance Criteria

- [ ] A three-row campaign is sent once through recording, journaled line by line, and a rerun prints three `skipped (journal)` lines and sends nothing.
- [ ] `send --dry-run` writes the rendered files with sanitised names, row numbers padded to at least two digits (D-16, owner decision), and lists the attachments, without a Mailer and without the journal.
- [ ] The phase's planning files and the sample module hold no workstation path, session id, private key or non-example address, so the owner can push them.

## Flagged assumptions

These are planner choices or open probe items. Each is reversible and visible to the owner at review time.

- **Campaign-wide build problems (RESEARCH Open Question 8).** A defect that every row shares (an unreadable attachment, an invalid `from`) is reported once per row, as `recipients.csv line <n>: <message>`. This is the simplest correct form; it is noisy only for large lists.
- **Dry-run I/O failure.** A failure while writing `--out` prints `Dry run stopped: <exception>` and exits 1 (an I/O failure during the run, like the journal write failure in D-13), not 2.
- **Jackson stays transitive.** The journal uses jackson-databind, which reaches the sample through the `morimail` dependency (RESEARCH "Alternatives Considered", verified). The sample POM gains only picocli.
- **Unclassified probe item CLI-12 (left unresolved).** Reviewed: the seam is two JDK types passed to the `SendCommand` constructor, and only `SerialMail.realMailer` changes in Phase 3 (CLI-14). Open: whether Phase 3's factory needs any CLI option besides the account file. Assumed not.
