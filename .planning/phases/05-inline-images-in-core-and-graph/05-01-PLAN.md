A Java developer can build a templated HTML mail with `cid:` images and send it through the Graph transport, with each image attached inline under its content ID.

This plan's slice: the tracer sends one templated mail with one inline image and one regular attachment from `Mail.using(...)` through `Mailer`, the registry, the Entra token stub and `GraphTransport` to WireMock, and proves the `isInline`/`contentId` JSON. Locked decision as amended (05-CONTEXT.md D-04, amendment of 2026-11-22, owner-approved in plan review):
- The reference pattern is `(?i)(?<![\p{L}\p{N}])cid:([^"'\s)>]*)` and an empty ID is skipped. Per the D-04 amendment, a `cid:` directly after a letter or digit is no reference (prose such as "acid:"), and a bare `cid:` (for example `href="cid:"`) is skipped, so it never produces the message "no inline image for cid:". Every other literal `cid:`, in markup or body text, still counts: `cid:x` after a quote, `=`, `(`, a space or a tag.

Choices (Claude's discretion per 05-CONTEXT.md, recorded here; the SUMMARY lists the first three for owner review):
- The ID that the scan reads from the rendered HTML can come from recipient data, so the message "no inline image for cid:X" shows X cut at 64 code points plus `...` (05-RESEARCH Open Question 4). Messages that name a caller-given content ID (unreferenced, duplicate, not an image) show it whole (D-14).
- D-06 is applied literally: `<` does not end a reference, so a text body such as `cid:logo</p>` reads the ID `logo</p` and fails. Accepted IDs can never contain `<` (D-09), so no accepted ID is cut short.
- Graph: bare `contentId`, no angle brackets, no `contentLocation` (documented as unsupported), and no `isInline: false` on regular attachments (05-RESEARCH Pattern 3). This keeps `GraphRequestTest.fullMailArrivesAsTheDocumentedJson` unchanged.
- Message texts: `contentId is blank`, `contentId contains a line break`, `contentId contains whitespace, a quote, a parenthesis or an angle bracket`, `inline image <id> has content type <type>, which is not an image type`, `duplicate inline content ID <id>` (each prefixed with `attachments[i]: `), then `no inline image for cid:<id>` and `inline image <id> is not referenced in the HTML body`.
- Check order inside the attachment loop: the existing file, file name and content type checks, then content ID shape, image type, duplicate. After the loop: missing image (references in first-seen order), then unreferenced image (inline images in the order added).
- No `validate` code for transports that cannot send inline images (D-02). `RecordingTransport` and `GraphTransport.validate` stay unchanged.
- `docs/spec.md` is not edited (Phase 8 owns it); Plan 05-02 records the deviation in `docs/architecture.md`.
