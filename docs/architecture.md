# morimail architecture

This page summarises the contracts of morimail and the reasons for them. It records every deviation from the spec (spec §5: signatures are binding in intent) and every difference from the Microsoft documentation.

## Contracts

- **One mail, one call.** `Mail.using(accountId)...build()`, then `Mailer.send(mail)`. The Mailer finds the account by id, applies `defaultFrom` and hands the message to the account's transport. Batching, retries, queues and scheduling belong to the consumer (spec §2).
- **Two extension points.** `TransportProvider` (`id()`, `create(options, auth)`) and `TokenProvider` (`accessToken(scope)`). The default method `freshAccessToken(scope, rejectedToken)` lets a transport get a new token after a 401 without importing `entra`. There is no other SPI (Rule 0).
- **Registry.** An explicit built-in list (`graph`) plus `ServiceLoader`. A duplicate or blank id fails with `IllegalStateException` when the registry loads. An unknown id fails with an `IllegalArgumentException` that lists the available ids. Options pass to the transport unread; the transport checks them in `create` and its size limits in `validate`.
- **Errors say what to do.** `build()` throws `InvalidMailException` naming the problem. `send` throws a checked `MailException`. `TransientMailException` means try again later, after `retryAfter()` when the service gave it. `PermanentMailException` means this mail will not be accepted as it is; beneath it are `InvalidMailException` (fix the mail) and `SenderRejectedException` (fix the sending mailbox or its grant). `AuthRequiredException` means fix the credentials or the consent. Configuration mistakes are unchecked `IllegalArgumentException` and `IllegalStateException`.
- **Accepted, not delivered.** A normal return means the service accepted the mail. A send that timed out may still have been accepted, so a retry can deliver twice: delivery is at-least-once. The Graph transport sends once and retries only a 401, once, with a fresh token.
- **Attachments.** `build()` checks that the files exist and are readable. A file that disappears before sending is an `InvalidMailException` that names the file and never carries its content. An attachment with a `contentId` is an inline image; `build()` checks its content ID, its image type and the `cid:` references of the HTML body in both directions, and the Graph limits count it like any other attachment.
- **Thread safety.** `Mailer`, `MailAccount`, transports and token providers are safe for concurrent use, and the records are immutable.
- **Imports.** The core imports only the JDK, apart from the built-in list. `graph` and `entra` do not import each other, so the lines they share (`Retry-After`, the cleaning of server text) are written twice on purpose. `ImportRulesTest` enforces this.
- **Logs and messages.** Nothing logs tokens, secrets, assertions or mail bodies, and a recipient address may appear at DEBUG only. `entra` writes no log records. `graph` writes one fixed INFO record per transport for a mail with both HTML and text.
- **Server text in messages.** A Graph failure message holds the HTTP status, `error.code` and `request-id` only. An Entra failure message quotes `error` and `error_description` (spec §7.3). These fields are cleaned: control characters become spaces, runs collapse, a text over 1000 characters is cut back to the last space before character 1000, anything that looks like a mail address becomes `<address>`, and the result is cut at 300 characters. This is a best-effort safeguard; the Entra description can still name the application and tenant ids.

## Deviations from the spec

| Spec | morimail | Reason |
|------|----------|--------|
| §7.3 (do not widen `TokenProvider`) | `TokenProvider` has a default method `freshAccessToken(String scope, String rejectedToken)` that delegates to `accessToken(scope)`. | The Graph transport can get a new token after a 401 without importing `entra`. Lambdas still work, and there is no new interface (CORE-02, owner decision). |
| §5.3 (data is `Map<String, Object>`) | `Mail.Builder.template(MailTemplate, Map<String, ?>)`. | Typed maps such as a CSV row `Map<String, String>` compile. Values still go through `String.valueOf` (owner decision). |
| §2 and §5.1 (error types unspecified) | An unknown transport id raises `IllegalArgumentException` that lists the available ids. A duplicate or blank provider id and a broken provider raise `IllegalStateException`. Invalid account configuration raises `IllegalArgumentException`. | Configuration errors surface when the account or registry is built and are not mail errors. The checked `MailException` tree stays for sending. |
| §3 (JUnit 5) | JUnit Jupiter 6.1.3 through `junit-bom`. | It is the current stable line, with the same `org.junit.jupiter` API and a Java 17 baseline (owner decision). |
| §10.1 (published as a test-jar) | The test-jar with `RecordingTransport` is built and shared inside the reactor only. The release profile sets `attach false` on it. Because an unattached test-jar is invisible to a packaging reactor, the release build runs on the published modules only (`-Prelease ... -pl morimail,morimail-html -am`). `morimail-html` takes `recording` from that test-jar for its tests, so its own `release` profile sets `default-testResources`, `default-testCompile` and `default-test` to phase `none`; the plain `verify` runs those tests. | The Central plugin would otherwise stage the test-jar, and spec §13.2 says the test-jar is not published (owner decision). |
| §7.1 (authority as a constructor option) | `EntraClientCredentials.authority(URI)` is a copy method that returns a new instance. The factories keep the spec signatures. | One way to point the token endpoint at a test server without a builder or overloads. |
| §7.2 (PKCS12 password) | The password is a `char[]`. The file must hold exactly one RSA key entry with its certificate. Any key-store problem is an `IllegalArgumentException` that names the file and never the password. | `KeyStore.load` convention, and a setup error is not a mail error. |
| G1 (timeouts) | The connect timeout (10 s) and request timeout (30 s) are fixed private constants in `entra` and `graph`. No option sets them. | Rule 0. They can become settable later without a break. |
| §6.1 (options) | The `graph` transport takes a second option, `baseUrl`, next to `saveToSentItems`. Unknown keys, a non-Boolean `saveToSentItems`, a `baseUrl` that is not an absolute https URL (http is accepted for `localhost`, `127.0.0.1` and `[::1]` only) and a missing `TokenProvider` are `IllegalArgumentException`s that name the key. The scope stays `https://graph.microsoft.com/.default`, so sovereign clouds need more work than a base URL. | Tests and the sample point the transport at WireMock. |
| §6.2 (3 MB, 4 MB) | "3 MB" is 3 x 1024 x 1024 bytes, per file and in total. The 4 MiB request limit is an estimate: base64 size of the attachments, the body as the JSON-escaped UTF-8 bytes that `send` writes, and a 16 KiB allowance. A file just under 3 MiB therefore fails the estimate, not the per-file rule. | Both are checked in `validate`, before any token request. |
| §6.3 (error table) | Statuses not in the table follow a class rule: 5xx transient, every other 4xx, 1xx and 3xx permanent. Redirects are never followed. A second 401 after the fresh-token retry is `SenderRejectedException` when `error.code` contains `mailbox` (case-insensitive), else `AuthRequiredException`. | One rule instead of a list, and one place for the live test to correct. |
| §6.3 (failure message) | A Graph failure message carries the HTTP status, the cleaned `error.code` and the `request-id`, nothing else. Graph's free-text `error.message` is never read into it. | In the live test, Graph's text for a 404 `ErrorInvalidUser` named the sender. The address reached the exception message and the live test output, and it would also reach the sample's stop line and journal. A pattern that replaces addresses in free text cannot be relied on, so the text is left out. This narrows GRAPH-08. |
| §6.3 (live results) | The error table in docs/spec.md has a live-status column from the live test of 2026-11-22: 202 for both credential flows, 403 `ErrorAccessDenied` and 404 `ErrorInvalidUser` as `SenderRejectedException`; the 401, 429/503/504, network, 400 and 413 rows are WireMock only. The forum report of a 401 for a sender without a mailbox is replaced by the 404 finding. A 403 also comes for minutes after a permission grant while Exchange applies it, so a 403 right after setup does not prove a wrong scope. | The spec asks for the table to be corrected after the live test. The live answers matched the mapping, so only the text changed and the code did not. |
| §6.3 and §7.3 (`Retry-After`) | `Retry-After` is read as seconds only, in `graph` and in `entra`, with the code written twice on purpose. Anything else, an HTTP date included, gives none. | `graph` and `entra` must not import each other. |
| §7.3 (token errors) | Every 4xx except 429, every 3xx and an unusable 200 (not JSON, no `access_token`, no positive `expires_in`) is an `AuthRequiredException`. 429, 5xx and network errors are transient. | The documented error is a 400, but other 4xx are possible, and a token that cannot be used cannot be retried into success. |
| §10.1 (test key store) | The key store is `morimail/src/test/resources/test-keystore-throwaway.p12`, password `changeit`, legacy PKCS12 (`keytool -J-Dkeystore.pkcs12.legacy`). | `keytool` rejects passwords shorter than six characters, and the legacy format loads on every JDK 17 patch level. |
| §10.1 (one live test) | The live test is one class, `LiveGraphTest`, with a main test, an inline-image test and two opt-in probe methods (out-of-scope mailbox, big attachment) that are skipped unless their variable is set. It is excluded by tag and run with `-Plive`. | One run answers the STOP report items; each probe prints one line the owner can paste. |
| §8.3 (rate default) | docs/spec.md §8.3 states the documented Exchange Online limits (30 messages per minute for SMTP client submission, which may not apply to Graph, and 10,000 recipients per day per mailbox) and that the owner confirmed the default of 20 mails per minute. `--rate` stays 20. | Spec §8.3 asks for the paragraph and the default to be checked after milestone 4. |
| §5 and §5.1 (contentId in build()) | `build()` accepts a non-null `contentId` as an inline image and applies the §10.3 checks (content ID not blank and free of whitespace, quotes, parentheses and angle brackets; an `image/` content type; unique content IDs; `cid:` references in both directions). The sentences in docs/spec.md §5 and §5.1 that say `build()` rejects a `contentId` still describe the MVP. | §10.3 replaces that MVP rule for milestone 6; the spec text is updated with the release docs. |
| §10.3 (cid: references) | A reference is `cid:` in any case that does not follow a letter or digit, in the HTML body only. Its ID ends at a double quote, an apostrophe, whitespace, `)`, `>` or the end of the body, is compared exactly and is never decoded; an empty ID is ignored. The content ID rules reject every character that ends an ID, so each accepted ID can be found. A failure message shows an ID read from the HTML cut at 64 code points. | One regular expression and no HTML parser (Rule 0); the letter-or-digit rule and the empty-ID rule (owner decision of 2026-11-22, the D-04 amendment) keep prose such as "acid:" from failing a mail; the ID can come from recipient data, hence the cut. |
| §10.3 (transport without inline images) | No `validate` code. | Both transports in this repository handle inline images (`graph` sends them, `recording` records them); the rule is for external transports (D-02). |
| §10.4 and §12 (`morimail-html` decisions) | A download failure is transient for a network error, a timeout, HTTP 5xx and 429, and invalid for every other failure. An image of 3 MiB or more is refused, as the Graph transport refuses it. A download has a 10 s connect timeout and one 30 s budget for headers and body together; the body is read on a thread of its own so the budget holds. A redirect is followed except from https to http. A `data:image/...;base64,` source is decoded through the work directory. `morimail` has compile scope in the helper's POM. | Spec §12 leaves these to the phase that builds the helper. Compile scope makes the helper's POM name the `morimail` version it is built against, so a consumer who declares only the helper gets a core with inline-image support (`morimail` 0.1.0 rejects every image the helper returns in `build()`). A consumer's own `morimail` dependency still wins under Maven's nearest-wins rule. Owner decision of 2026-11-23 (gap G-07-2), replacing the earlier `provided` scope. |

## Differences from the Microsoft documentation

Read on 2026-11-22. Where a page differs from the spec, the library follows the page and the difference is listed here.

- One body: the message resource has a single `body` (HTML or text), so the transport sends HTML when present, else text. A mail with both is logged once; sending both would need MIME.
- 4 MiB request limit: not stated on the sendMail, errors, throttling or large-attachments pages. The only source is a Microsoft Q&A answer ("generally around 4 MB", then a 413). The constant is kept as an estimate. The live probes of 2026-11-22 did not contradict it.
- 3 MiB attachment limit: the large-attachments page names 3 MB for a single POST to a message's `attachments` property. The sendMail page states no attachment limit. The 3 MiB rule is conservative and applies to `sendMail` by inference. Live on 2026-11-22, attachments of 2,900,000 and 3,100,000 bytes were accepted. The second is above 3 MB and, as base64, above 4 MB in decimal units, so the binary reading holds. Where the service starts to refuse was not probed.
- `saveToSentItems`: the sendMail page types it as Boolean ("specify it only if the parameter is false") but its examples show the string `"false"`. The library sends the JSON boolean `false`, and only when the option is false.
- Inline images (read on 2026-11-22): the sendMail page has no inline example, and its file-attachment example is a plain text file. The library follows the fileAttachment, attachment and attachmentItem resource pages, so a file attachment marked inline carries `"isInline": true` and `"contentId"` with the bare content ID that the HTML body refers to as `cid:<contentId>`, without angle brackets. `contentLocation` is not sent, because the fileAttachment page says not to use it. Regular attachments carry no `isInline` key (the attachment page names false as the other value, and Microsoft's sendMail example omits the key). The fileAttachment page calls `contentId` the ID in the Exchange store, and the attachmentItem page calls it the CID for `<img src="cid:contentId">`; the library uses the second meaning. Live status: not yet confirmed, the owner runs `LiveGraphTest.sendsOneMailWithAnInlineImage`.
- Entra assertion: PS256, the `x5t#S256` header and the claims (`aud`, `iss`, `sub`, `jti`, `nbf`, `iat`, `exp`) match the certificate-credentials page. The client-credentials page still shows an RS256 sample assertion. There is no RS256 fallback; Entra accepted the PS256 assertion with `x5t#S256` in the live test on 2026-11-22.
- Token response: the documented body has `access_token`, `token_type` and a numeric `expires_in`. The library reads only the token and a numeric `expires_in` (a string value makes the response unusable), clamps `expires_in` to one year and always sends `Bearer`.
- Token errors: the documented example is a 400 with `error`, `error_description` and more fields. Every 4xx except 429 is treated the same way.
- Error body: the errors page spells the inner error `innerError` in its example and `innererror` in its property table. The code reads both.
- `request-id`: the errors page does not name the response header. The code reads the `request-id` header first, then the inner error.
- `Retry-After`: the throttling page documents seconds only, and the library reads only seconds. An HTTP-date value is treated as absent.
- `from`: the message `from` property must match the mailbox in the URL, and changing it needs send-as rights, so the body carries no `from`; the mailbox is in the path.
- Limits: the Outlook service limits (10,000 requests per 10 minutes, four concurrent requests, 150 MB upload per 5 minutes per app and mailbox, 500 recipients per message) are far above a serial sender at 20 mails per minute. No code uses them.
- Character escapes in the size estimate: Jackson writes a character outside the Basic Multilingual Plane (an emoji) in a JSON string as a surrogate escape pair of 12 bytes, not as 4 UTF-8 bytes. Other non-ASCII characters such as an umlaut stay raw (2 bytes). The estimate measures the body with the mapper that `send` uses, so it counts what is posted.
- The mailbox error code for an unlicensed or missing mailbox is not documented. Live, a sender without an Exchange mailbox got 404 `ErrorInvalidUser` (the 404 row), not a 401. `error.code` containing `mailbox` on a second 401 is still an assumption that no real answer has tested.
- Roles for the scoped path (read on 2026-11-22 while writing `docs/entra-setup.md`): the RBAC for Applications page requires the Exchange Administrator role in Microsoft Entra ID as well as the Organization Management role group in Exchange Online. Spec §9 step 6 names only Organization Management. The guide names both.
- `Test-ServicePrincipalAuthorization` (same reading): the page says the cmdlet excludes permissions granted separately in Microsoft Entra ID. `InScope` True therefore does not show that the union trap is cleared. The guide also tells the admin to check the Admin consent tab.
- Scope filters (read on 2026-11-22): the recipient-filter properties page says not to use `PrimarySmtpAddress` and to use `EmailAddresses` instead. The guide's example filter uses `Alias`, which is single-valued, and tells the admin to confirm `InScope` on the real mailbox.
- Sending limits (the Exchange Online limits page, read on 2026-11-22): the page gives 30 messages per minute as a limit for SMTP client submission. It does not say whether Graph `sendMail` counts against it, so the README, the guide and the spec say it is documented for SMTP client submission and not confirmed for Graph. The page also documents a tenant external recipient rate limit, and 100 external recipients per 24 hours with NDR 550 5.7.236 for senders on `onmicrosoft.com` domains. The spec mentions neither. The guide tells the owner to send from a verified custom domain.
